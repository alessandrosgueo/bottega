## 1. La sessione corrente, per porta

Come fa un comando lanciato dal modello (uno strumento Bash o shell) a sapere quale trascrizione è la sua da dentro una sessione.

### Claude Code (`claude`)
- **Variabili d'ambiente rilevate:**
  - `CLAUDE_CODE_SESSION_ID`: contiene l'identificativo UUID della sessione corrente.
  - Altre variabili presenti nel processo: `CLAUDECODE=1` (marker di processo), `CLAUDE_PID`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_EFFORT`.
  - Fonte: osservato sui file locali (`env | cut -d= -f1 | sort`, solo nomi) e `docs/ricognizioni/2026-11-08-porte.md:43,48`.
- **Trascrizione corrispondente:**
  - Percorso: `~/.claude/projects/<progetto>/<session-id>.jsonl` dove `<session-id>` coincide con il valore di `CLAUDE_CODE_SESSION_ID` e `<progetto>` è il percorso della cartella di lavoro normalizzato (caratteri non alfanumerici sostituiti da `-`).
- **Regola di riserva (senza variabile):**
  - Nella cartella `~/.claude/projects/<progetto>/`, selezionare il file `<session-id>.jsonl` con data di ultima modifica (`mtime`) più recente.

### Antigravity (`agy`)
- **Variabili d'ambiente rilevate:**
  - `ANTIGRAVITY_CONVERSATION_ID`: identificativo UUID della conversazione corrente.
  - `ANTIGRAVITY_APP_DATA_DIR`: cartella dati dell'applicazione (es. `~/.gemini/antigravity-cli`).
  - `ANTIGRAVITY_TRAJECTORY_ID`: identificativo della traiettoria corrente.
  - Altre variabili presenti nel processo: `AI_AGENT`, `ANTIGRAVITY_AGENT`, `ANTIGRAVITY_AGENTAPI_EXE`, `ANTIGRAVITY_CSRF_TOKEN`, `ANTIGRAVITY_LS_ADDRESS`, `ANTIGRAVITY_LS_VERSION`, `ANTIGRAVITY_PROJECT_ID`, `ANTIGRAVITY_SOURCE_METADATA`.
  - Fonte: osservato sui file locali (`env | cut -d= -f1 | sort`, solo nomi) e documentazione CLI headless (`https://antigravity.google/docs/cli/headless`).
- **Trascrizione corrispondente:**
  - Database SQLite: `<ANTIGRAVITY_APP_DATA_DIR>/conversations/<ANTIGRAVITY_CONVERSATION_ID>.db`
  - Log e trascrizione JSONL: `<ANTIGRAVITY_APP_DATA_DIR>/brain/<ANTIGRAVITY_CONVERSATION_ID>/.system_generated/logs/transcript.jsonl` (e `transcript_full.jsonl`).
- **Regola di riserva (senza variabile):**
  - Nella cartella `<ANTIGRAVITY_APP_DATA_DIR>/brain/` o `conversations/`, selezionare la cartella o il file `.db` con data di ultima modifica (`mtime`) più recente.

### Pi (`pi`)
- **Variabili d'ambiente rilevate:**
  - `PI_SESSION_FILE`: percorso assoluto diretto al file JSONL della sessione corrente.
  - `PI_SESSION_ID`: identificativo della sessione corrente.
  - Variabili ausiliarie iniettate nei comandi shell: `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`.
  - Marker di processo: `AI_AGENT=pi`, `PI_CODING_AGENT=true`.
  - Fonte: pacchetto npm `@earendil-works/pi-coding-agent` 1.5.0, `docs/environment-variables.md` (sezione «Shell Tool Session Environment»).
- **Trascrizione corrispondente:**
  - Percorso: indicato direttamente da `PI_SESSION_FILE` (tipicamente `~/.pi/agent/sessions/--<cartella>--/<timestamp>_<session-id>.jsonl`).
- **Regola di riserva (senza variabile):**
  - Nella cartella di sessione del progetto `~/.pi/agent/sessions/--<cartella>--/`, selezionare il file `.jsonl` con `mtime` più recente.

### GitHub Copilot CLI (`copilot`)
- **Variabili d'ambiente rilevate:**
  - `COPILOT_AGENT_SESSION_ID`: identificativo di sessione iniettato esplicitamente nell'ambiente di esecuzione dei tool shell/bash dalla CLI.
  - Fonte: pacchetto npm `@github/copilot` 1.0.32, `app.js` (chiamata a creazione shell: `Syt.create(..., { COPILOT_AGENT_SESSION_ID: this.config.sessionId })`).
- **Trascrizione corrispondente:**
  - Percorso: `~/.copilot/session-state/<COPILOT_AGENT_SESSION_ID>/events.jsonl` (e `workspace.yaml`).
- **Regola di riserva (senza variabile):**
  - In `~/.copilot/session-state/`, scorrere le cartelle `<uuid>/` esaminando `workspace.yaml`: filtrare quelle con `cwd` corrispondente alla cartella di lavoro corrente e scegliere quella con timestamp `updated_at` (o `mtime` di `events.jsonl`) più recente.

## 3. La quota in token, per porta

Come calcolare «quanto ha speso» una sessione tra due istanti e se la trascrizione cresce per record con indicazione temporale.

### Risposta generale
In tutte e quattro le porte le trascrizioni crescono in modo append-only, riga per riga (record JSONL). Ogni riga contiene un campo orario esplicito in formato ISO 8601 (o equivalente), che permette di filtrare i record compresi nell'intervallo temporale $[t_1, t_2]$ e sommare i rispettivi contatori.

### Dettaglio per porta

| Porta | File di trascrizione | Campo orario nel record | Record da selezionare | Contatori da sommare |
|---|---|---|---|---|
| **Claude Code** | `~/.claude/projects/<progetto>/<session-id>.jsonl` | `timestamp` (ISO 8601) | `type == "assistant"` | `message.usage.input_tokens` + `message.usage.cache_creation_input_tokens` + `message.usage.cache_read_input_tokens` + `message.usage.output_tokens` |
| **Antigravity** | `<appDataDir>/brain/<id>/.system_generated/logs/transcript.jsonl` | `created_at` (ISO 8601; anche progressivo `step_index`) | `source == "MODEL"` (`type == "PLANNER_RESPONSE"`) | `input_tokens` + `output_tokens` + `cache_read_tokens` (totale per passo coerente con `total_tokens` headless) |
| **Pi** | `~/.pi/agent/sessions/--<cartella>--/<timestamp>_<session-id>.jsonl` | `timestamp` (ISO 8601 a livello di entry; `message.timestamp` in ms) | `type == "message"` (`role == "assistant"`), `type == "usage"`, `type == "compaction"`, `type == "branch_summary"` | `usage.input` + `usage.output` + `usage.cacheRead` + `usage.cacheWrite` (o direttamente `usage.totalTokens`) |
| **Copilot CLI** | `~/.copilot/session-state/<uuid>/events.jsonl` | `timestamp` (ISO 8601 dell'evento) | `type == "assistant.usage"` (ed eventuali `subagent.completed`) | `data.inputTokens` + `data.outputTokens` + `data.cacheReadTokens` + `data.cacheWriteTokens` (e `data.totalTokens` per sotto-agenti) |

## 4. I campi del Project v2 di GitHub

### Tipi di campo esistenti in Project v2
- Tipi di campi personalizzati definiti dall'enum GraphQL `ProjectV2CustomFieldType`:
  - `TEXT`
  - `NUMBER`
  - `DATE`
  - `SINGLE_SELECT`
  - `MULTI_SELECT`
  - `ITERATION`
- Fonte: schema GraphQL GitHub (introspezione query `__type(name: "ProjectV2CustomFieldType")`).

### Scrittura di un `NUMBER` con `updateProjectV2ItemFieldValue`
- L'input GraphQL `ProjectV2FieldValue` possiede il campo `number` di tipo scalare `Float`:
  - `value: { number: 123.45 }`
- Chiamando l'API tramite la CLI `gh`:
  - Se si usano gli argomenti a riga di comando: `-F value[number]=<valore>` (con il flag maiuscolo `-F` di `gh api` per passare un tipo non-stringa / numerico), oppure inviando il payload JSON via stdin/query.
- Fonte: schema GraphQL GitHub (`__type(name: "ProjectV2FieldValue")`).

### Creazione di un campo con `createProjectV2Field`
- Mutation: `mutation($input: CreateProjectV2FieldInput!) { createProjectV2Field(input: $input) { projectV2Field { ... } } }`
- Argomenti dell'oggetto `CreateProjectV2FieldInput`:
  - `projectId: ID!` (obbligatorio: ID GraphQL del Project v2)
  - `dataType: ProjectV2CustomFieldType!` (obbligatorio: `TEXT`, `NUMBER`, `DATE`, `SINGLE_SELECT`, `MULTI_SELECT`, `ITERATION`)
  - `name: String!` (obbligatorio: nome visibile del campo)
  - `singleSelectOptions: [ProjectV2SingleSelectFieldOptionInput!]` (opzionale, per opzioni di `SINGLE_SELECT`)
  - `multiSelectOptions: [ProjectV2SingleSelectFieldOptionInput!]` (opzionale, per opzioni di `MULTI_SELECT`)
  - `iterationConfiguration: ProjectV2IterationFieldConfigurationInput` (opzionale, per configurazione di `ITERATION`)
  - `clientMutationId: String` (opzionale)
- **Limite campi:** massimo **50 campi personalizzati** per Project v2 (documentazione GitHub Projects v2 e query GraphQL in `board.py:54,130` con `fields(first: 50)`).
- Fonte: schema GraphQL GitHub (`__type(name: "CreateProjectV2FieldInput")`).

### Situazione in `attrezzi/bottega/board.py`
- **Come scrive oggi `BoardProject.campo`:**
  - Posizione: `attrezzi/bottega/board.py:407-453`.
  - Gestisce esclusivamente:
    1. `valore is None`: azzera il campo eseguendo `_MUTATION_CLEAR` (`clearProjectV2ItemFieldValue`, righe 419-427).
    2. `SINGLE_SELECT` (`is_select`, righe 429-443): cerca l'opzione per nome ed esegue `_MUTATION_UPDATE` con `-f value[singleSelectOptionId]={opt_id}`.
    3. Qualsiasi altro tipo (`else`, righe 444-453): scrive ciecamente come testo `-f value[text]={valore}`.
- **Cosa manca per i numeri:**
  1. Riconoscimento del tipo di dato: manca il controllo `field_info.get("dataType") == "NUMBER"`. Se il campo nel Project è un `NUMBER`, l'invio di `value[text]` fallisce con errore GraphQL di tipo incompatibile.
  2. Costruzione del valore numerico per GraphQL: serve passare `-F value[number]={valore}` (usando `-F` per mantenere la natura numerica) o serializzare `{"number": float(valore)}`, assicurando la conversione o validazione di `valore` come numero (`int` o `float`).
  3. Firma e tipizzazione: la firma del protocollo `Board.campo` (`board.py:43`) e del metodo `BoardProject.campo` (`board.py:407`) accetta `valore: str | None`. Per i numeri deve accettare anche `int | float`.

## 5. La scelta viva

### Dati letti per costo atteso e probabilità di unione in `attrezzi/bottega/scelta.py`
- Funzione di calcolo: `_scegli_per_costo_atteso` (`attrezzi/bottega/scelta.py:410-456`).
- Parametri in ingresso (`scelta.py:410-416`):
  - `con_quota: list[Candidato]`
  - `compito: Compito`
  - `configurazione: Configurazione`
  - `risultati: Mapping[tuple[str, str], Risultati]` (parametro `risultati`, riga 413)
  - `caso: random.Random`
  - `costo_decisore: float` (riga 415; predefinito 1.0 in `scegli` a riga 71)
  - `costi_propri: Mapping[str, float] | None` (riga 416; predefinito None in `scegli` a riga 72)
- Estrazione dei conteggi storici tramite `_conteggia_risultati` (`scelta.py:459-473`):
  - Dalla mappa `risultati[(candidato_id, etichetta)]` (o fallback su `(candidato_id, "*")`):
    - `uniti` (`u`)
    - `corretti` (`cr`)
    - `rifiutati` (`rf`)
- Calcolo probabilità di unione $p$ (campionamento di Thompson su distribuzione Beta, righe 421-423):
  - `a = 1.0 + u`
  - `b = 1.0 + cr + rf`
  - `p = max(caso.betavariate(a, b), 1e-9)`
- Calcolo costo atteso (righe 424-428):
  - `peso_quota = PESI_QUOTA.get(bottega.quota, 1.0)` con `PESI_QUOTA = {"scarsa": 1.0, "normale": 0.25, "abbondante": 0.0}` (`scelta.py:27-31`).
  - `c_proprio = costi_propri.get(c.id, 1.0) if costi_propri else 1.0` (riga 426).
  - `numeratore = costo_decisore + peso_quota * c_proprio` (riga 427).
  - `costo = numeratore / p` (riga 428).

### Da dove B3 li prende oggi
- In `attrezzi/bottega/distributore.py`:
  - A riga 465, chiama `scegli(...)` passando `risultati={}` (dizionario vuoto). Non passa `costi_propri` né `costo_decisore` (usa i valori predefiniti).
- In `attrezzi/bottega/giro.py`:
  - A riga 824 (consulto dell'esecutore), chiama `scegli(...)` passando `risultati={}` (dizionario vuoto).
  - A riga 1165 (rilettura del consigliere prima della consegna), chiama `scegli(...)` passando `risultati={}` (dizionario vuoto).
- In sintesi: in B3 l'infrastruttura di calcolo matematico della scelta viva è completa in `scelta.py`, ma `distributore.py` e `giro.py` passano sempre `{}` come `risultati`. Di conseguenza i parametri Beta partono sempre dal prior non informativo $a=1, b=1$, e il costo proprio è sempre 1.0.

## 6. Il banco di prova

### Come è fatto un caso in `casistica/` e `attrezzi/bottega/casi.py`
- **Fonti:** `casistica/LEGGIMI.md:8-28`, `attrezzi/bottega/casi.py:1-31, 37-52, 270-345`.
- **Organizzazione dei file:**
  - Un file per area: `casistica/<area>.md` (nome del file minuscolo, estensione `.md` minuscola; `LEGGIMI.md` è escluso).
- **Struttura del caso:**
  - Intestazione di livello 3: `### <ID>. <titolo>` (riga 21 di `casi.py`), con `<ID>` che inizia con l'area in maiuscolo e numero progressivo (es. `CICLO-1`, `PORTE-1`).
  - Sequenza obbligatoria di 7 campi ordinati, ciascuno a inizio riga con etichetta in grassetto `**Nome:**`:
    1. `**Scenario:**` (descrizione della situazione, testo non vuoto)
    2. `**Domanda:**` (il quesito decisionale, testo non vuoto)
    3. `**Opzioni:**` (elenco puntato con sintassi `- <LETTERA>) <testo>`; righe rientrate continuano il testo)
    4. `**Scelta:**` (una singola lettera maiuscola, corrispondente a una delle opzioni: permette il confronto deterministico senza modello LLM)
    5. `**Perché:**` (motivazione sintetica della scelta, testo non vuoto)
    6. `**Esito:**` (com'è andata o «da vedere», testo non vuoto)
    7. `**Fonte:**` (origine della decisione: `deciso dall'utente`, `di chi decide` o `dal vivo AAAA-MM-GG` con data ISO valida)

- **Sottocomando CLI:** `bottega casi [--cartella PERCORSO] [--domande]`.
- **Funzionalità implementate:**
  1. **Controllo e validazione del formato (`comando_casi` senza `--domande`, `casi.py:98-120`):**

## Cosa non ho trovato

1. **Specifiche interne o schema formale del database SQLite `conversations/<id>.db` di Antigravity:** Google non documenta pubblicamente le tabelle interne di SQLite né la struttura dei messaggi binari Protocol Buffers ivi memorizzati. La presenza dei contatori di token è stata invece riscontrata e verificata nei file `brain/<id>/.system_generated/logs/transcript.jsonl`.
2. **Meccanismo di persistenza e recupero dei risultati storici in B3:** in `distributore.py` e `giro.py` non è presente alcun codice che carichi dati passati o popoli il parametro `risultati` della funzione `scegli(...)` (viene sempre passato `{}`).
3. **Documentazione ufficiale esplicita per le variabili d'ambiente iniettate nella shell di GitHub Copilot CLI:** le pagine di riferimento dei documenti web di GitHub non elencano sistematicamente le variabili di sessione iniettate nei tool shell; il nome `COPILOT_AGENT_SESSION_ID` è stato individuato direttamente dall'analisi del codice JavaScript nel pacchetto npm `@github/copilot@1.0.32`.
