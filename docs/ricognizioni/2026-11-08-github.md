# Ricognizione GitHub per la Tappa B3 (Metodo «Bottega»)

Questo documento raccoglie gli esiti della ricognizione tecnica sulle API, sui comandi di `gh` CLI e sui comportamenti di GitHub Actions per la regia della bottega.

---

## 1. Projects (v2) di un Account Personale

### Elencare gli elementi con i valori dei campi
- **CLI (`gh`):**
  ```bash
  # Elenco in formato JSON con tutti i campi
  gh project item-list <numero_progetto> --owner <proprietario> --format json

  # Visualizzazione con colonne extra specifiche
  gh project item-list <numero_progetto> --owner <proprietario> --field "Status" --field "Priority"
  ```
- **GraphQL API:**
  Endpoint: `POST https://api.github.com/graphql`
  Query:
  ```graphql
  query($owner: String!, $number: Int!) {
    user(login: $owner) {
      projectV2(number: $number) {
        id
        title
        items(first: 100) {
          nodes {
            id
            fieldValues(first: 20) {
              nodes {
                ... on ProjectV2ItemFieldTextValue {
                  text
                  field { ... on ProjectV2FieldCommon { name } }
                }
                ... on ProjectV2ItemFieldNumberValue {
                  number
                  field { ... on ProjectV2FieldCommon { name } }
                }
                ... on ProjectV2ItemFieldDateValue {
                  date
                  field { ... on ProjectV2FieldCommon { name } }
                }
                ... on ProjectV2ItemFieldSingleSelectValue {
                  name
                  optionId
                  field { ... on ProjectV2FieldCommon { name } }
                }
              }
            }
            content {
              ... on Issue { number title url }
              ... on PullRequest { number title url }
              ... on DraftIssue { title body }
            }
          }
        }
      }
    }
  }
  ```

### Modificare un campo (single-select, text, number, date)
- **CLI (`gh project item-edit`):**
  ```bash
  # Campo a scelta singola (per nome o per option ID)
  gh project item-edit <numero_progetto> --owner <proprietario> --url <url_issue_o_pr> --field "Status" --value "In Progress"
  # oppure tramite ID GraphQL:
  gh project item-edit --id <item_id> --project-id <project_id> --field-id <field_id> --single-select-option-id <option_id>

  # Campo di testo
  gh project item-edit <numero_progetto> --owner <proprietario> --url <url_issue_o_pr> --field "Note" --text "Aggiornamento bottega"

  # Campo numerico
  gh project item-edit <numero_progetto> --owner <proprietario> --url <url_issue_o_pr> --field "Stima" --number 5

  # Campo data (formato YYYY-MM-DD)
  gh project item-edit <numero_progetto> --owner <proprietario> --url <url_issue_o_pr> --field "Scadenza" --date "2026-11-30"

  # Svuotare un campo
  gh project item-edit --id <item_id> --project-id <project_id> --field-id <field_id> --clear
  ```
- **GraphQL Mutation:**
  ```graphql
  mutation($projectId: ID!, $itemId: ID!, $fieldId: ID!, $value: ProjectV2FieldValue!) {
    updateProjectV2ItemFieldValue(
      input: {
        projectId: $projectId
        itemId: $itemId
        fieldId: $fieldId
        value: $value
      }
    ) {
      projectV2Item { id }
    }
  }
  ```
  Dove `$value` contiene `{ singleSelectOptionId: "..." }`, `{ text: "..." }`, `{ number: 42 }` o `{ date: "2026-11-30" }`.

### Creare un campo e aggiungere un'opzione a un campo single-select senza perdere i valori esistenti
- **Creare un campo:**
  ```bash
  # Creazione campo testo
  gh project field-create <numero_progetto> --owner <proprietario> --name "Priorità" --data-type "TEXT"

  # Creazione campo single-select con opzioni
  gh project field-create <numero_progetto> --owner <proprietario> --name "Fase" --data-type "SINGLE_SELECT" --single-select-options "In attesa,In lavorazione,Completato"
  ```
  GraphQL: mutation `createProjectV2Field(input: { projectId: $projectId, dataType: SINGLE_SELECT, name: "...", singleSelectOptions: [...] })`.
- **Aggiungere un'opzione a un campo single-select esistente senza perdere i valori esistenti:**
  - **Via API / CLI:** Non supportato / mutazione assente. Non esiste nell'API GraphQL una mutation di tipo `updateProjectV2SingleSelectField` o `updateProjectV2Field` per aggiornare le opzioni di configurazione di un campo esistente, e `gh` non possiede un comando `field-edit`.
  - **Via Interfaccia Web GitHub:** È il metodo ufficiale raccomandato. Andare su **Project Settings > Fields**, cliccare sul campo a scelta singola, premere **+ Add option** e salvare. In questo modo la nuova opzione viene aggiunta all'elenco e tutti i valori precedentemente assegnati agli item del progetto restano intatti.

### Limite al numero dei campi
- Un progetto GitHub Projects (v2) supporta al massimo **50 campi in totale** (somma complessiva di campi custom, campi di sistema predefiniti e campi issue).
- I campi custom di tipo single-select supportano fino a **100 opzioni**.

### Scope del token
- **Personal Access Token (classic):**
  - Lettura e scrittura: scope `project`.
  - Sola lettura: scope `read:project`.
- **Nota sui Fine-grained Personal Access Tokens:** Non supportano i progetti appartenenti ad account personali (`users`), sono supportati unicamente per progetti di organizzazione (`orgs`). Per account personali è obbligatorio usare un PAT classic con scope `project`.

**Fonti:**
- `gh project --help`, `gh project item-list --help`, `gh project item-edit --help`, `gh project field-create --help`
- https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects
- https://docs.github.com/en/graphql/reference/mutations#createprojectv2field
- https://docs.github.com/en/graphql/reference/mutations#updateprojectv2itemfieldvalue

## 2. Sotto-issue (Sub-issues)

### Elencare e aggiungere sotto-issue (REST e GraphQL)
- **REST API:**
  - **Elencare sotto-issue di una issue:**
    - Metodo: `GET /repos/{owner}/{repo}/issues/{issue_number}/sub_issues`
    - Parametri: `per_page` (max 100), `page`
    - Header: `Accept: application/vnd.github+json`
    - Permesso token: `Issues` (read) o scope PAT `repo`.
  - **Aggiungere una sotto-issue:**
    - Metodo: `POST /repos/{owner}/{repo}/issues/{issue_number}/sub_issues`
    - Body JSON:
      ```json
      {
        "sub_issue_id": 123456789,
        "replace_parent": false
      }
      ```
      *(Nota: `sub_issue_id` è l'ID di database numerico globale della issue figlia, ottenibile via API da `.id`).*
    - Permesso token: `Issues` (write) o scope PAT `repo`.
  - **Riordinare / cambiare priorità:**
    - Metodo: `PATCH /repos/{owner}/{repo}/issues/{issue_number}/sub_issues/priority`
    - Body JSON: `{"sub_issue_id": 123456789, "after_id": 987654321}` oppure `{"before_id": ...}`.
  - **Rimuovere una sotto-issue:**
    - Metodo: `DELETE /repos/{owner}/{repo}/issues/{issue_number}/sub_issue`
    - Body JSON: `{"sub_issue_id": 123456789}`.
- **GraphQL API:**
  - **Elencare:**
    ```graphql
    query($owner: String!, $repo: String!, $issueNumber: Int!) {
      repository(owner: $owner, name: $repo) {
        issue(number: $issueNumber) {
          id
          title
          parent { id number title }
          subIssues(first: 50) {
            nodes {
              id
              number
              title
              state
            }
          }
          subIssuesSummary {
            total
            completed
            percentCompleted
          }
        }
      }
    }
    ```
  - **Aggiungere:**
    ```graphql
    mutation($parentIssueId: ID!, $childIssueId: ID!) {
      addSubIssue(input: {
        issueId: $parentIssueId
        subIssueId: $childIssueId
      }) {
        issue { id number }
        subIssue { id number }
      }
    }
    ```
    *(Nota: in fase di creazione di una nuova issue è possibile passare direttamente `parentIssueId` nella mutation `createIssue`).*
  - **Riordinare:** mutation `reprioritizeSubIssue(input: { issueId: $parentId, subIssueId: $childId, afterId: $afterId })`.
  - **Rimuovere:** mutation `removeSubIssue(input: { issueId: $parentId, subIssueId: $childId })`.

### Ordine in cui tornano le sotto-issue
Tornano nell'**ordine di visualizzazione / priorità** (display order) configurato sulla issue madre.
- Per impostazione predefinita, le sotto-issue aggiunte successivamente vengono inserite in coda (in fondo all'elenco).
- L'ordine può essere modificato manualmente nell'interfaccia web (trascinamento drag-and-drop) oppure via API chiamando `PATCH .../sub_issues/priority` (o mutation `reprioritizeSubIssue`).

### Supporto nel comando `gh`
Sì, `gh` supporta nativamente la gestione delle sotto-issue tramite il comando `gh issue edit`:
- **Aggiungere una sotto-issue:**
  ```bash
  # Dalla issue padre aggiungendo la figlia per numero o URL:
  gh issue edit <numero_padre> --add-sub-issue <numero_figlia>

  # Oppure dalla issue figlia impostando la issue padre:
  gh issue edit <numero_figlia> --parent <numero_padre>
  ```
- **Rimuovere una sotto-issue:**
  ```bash
  gh issue edit <numero_padre> --remove-sub-issue <numero_figlia>
  # oppure:
  gh issue edit <numero_figlia> --remove-parent
  ```
- **Elencare / visualizzare:**
  ```bash
  # Visualizzazione dei campi JSON subIssues e subIssuesSummary
  gh issue view <numero_issue> --json subIssues,subIssuesSummary
  ```
  *(Nota: non esiste un comando dedicato `gh sub-issue`, la gestione è integrata in `gh issue edit` e `gh issue view`).*

**Fonti:**
- `gh issue edit --help`, `gh issue view --help`
- https://docs.github.com/en/rest/issues/sub-issues
- https://docs.github.com/en/graphql/reference/mutations#addsubissue

## 3. Workflow Riusabili (Reusable Workflows)

### `on: workflow_call`, input e segreti (`secrets: inherit`)
- Nel workflow riusabile chiamato (es. `.github/workflows/esecutore.yml`):
  ```yaml
  name: Esecutore Bottega
  on:
    workflow_call:
      inputs:
        task-id:
          description: 'Identificativo task'
          required: true
          type: string
        verbose:
          required: false
          type: boolean
          default: false
      secrets:
        BOTTEGA_TOKEN:
          description: 'Token di bottega'
          required: false
  ```
- Nel workflow chiamante (caller):
  ```yaml
  jobs:
    invoca-bottega:
      uses: <proprietario>/<repo>/.github/workflows/esecutore.yml@v1
      with:
        task-id: 'TASK-42'
      secrets: inherit
  ```
  Con `secrets: inherit` tutti i segreti del repository chiamante vengono passati implicitamente al workflow chiamato senza doverli mappare uno a uno.

### Chiamare un workflow riusabile da un altro repository
Sintassi:
```yaml
uses: <proprietario>/<repo>/.github/workflows/<file>.yml@<ref>
```
Dove `<ref>` può essere un tag Git (`@v1.0.0`), un ramo (`@main`) o un commit SHA (`@8f45a...`).

### Condizioni d'accesso per repository privato vs pubblico
- **Repository pubblico:**
  Il workflow riusabile è accessibile da qualsiasi altro repository su GitHub (pubblico o privato), senza configurazioni particolari.
- **Repository privato:**
  - **Stesso repository:** accessibile direttamente, anche con percorso relativo (es. `./.github/workflows/<file>.yml`).
  - **Altro repository:**
    - Può essere chiamato **esclusivamente** da repository che risiedono all'interno dello **stesso account utente** (o della stessa organizzazione/enterprise). Non è consentita la condivisione di workflow riusabili privati tra account proprietari differenti.
    - **Impostazione «Access» nel repository privato chiamato:**
      Nel repository privato che ospita il workflow: andare su **Settings > Actions > General > Access**, e selezionare l'opzione:
      *“Accessible from repositories owned by the user account '<proprietario>'”* (oppure *“Accessible from repositories in the '<organizzazione>' organization”*).
    - **Funzionamento token:** GitHub inietta automaticamente sul runner un token di installazione con ambito temporaneo (durata 1 ora) che garantisce l'accesso in lettura al repository privato chiamato per scaricare il workflow.

**Fonti:**
- https://docs.github.com/en/actions/sharing-automations/reusing-workflows
- https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#managing-access-to-actions-and-reusable-workflows

## 4. `concurrency`

### Comportamento con `cancel-in-progress: false`
Configurazione:
```yaml
concurrency:
  group: bottega-esecutore
  cancel-in-progress: false
```
Regole applicate da GitHub Actions:
1. **Un solo giro in esecuzione:** All'interno del gruppo di concorrenza può essere in stato `running` al massimo un solo job o workflow alla volta.
2. **Coda con `queue: single` (default):** Può restare in attesa (`pending`) al massimo **un solo giro**.
3. **Arrivo di un nuovo giro mentre un altro è già in coda:**
   - Il giro attualmente in esecuzione (`running`) non viene interrotto e procede regolarmente fino al termine.
   - Il giro che era già in attesa (`pending`) viene **annullato e scartato** (canceled).
   - Il **nuovo giro** appena arrivato prende il suo posto e diventa l'unico giro in attesa.
4. **Quanti ne restano in attesa:** Esattamente **uno** (l'ultimo arrivato). Tutti i giri intermedi arrivati mentre il primo era in esecuzione vengono persi/annullati.

*(Nota: per conservare fino a 100 giri in coda senza cancellare gli intermedi è possibile configurare `queue: max`, ma tale parametro non può essere combinato con `cancel-in-progress: true`).*

**Fonti:**
- https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs

## 5. Giri che ne Fanno Partire Altri (Trigger a Cascata)

### La regola anti-loop con `GITHUB_TOKEN`
Per evitare loop ricorsivi infiniti e costi fuori controllo, le modifiche effettuate all'interno di un workflow utilizzando il token automatico del giro (`GITHUB_TOKEN` o `secrets.GITHUB_TOKEN`) **non generano nuovi workflow run**.
Se un workflow esegue un `git push` o crea una release usando `GITHUB_TOKEN`, i workflow configurati su `on: push` o `on: release` non partiranno.

### Eccezioni con `GITHUB_TOKEN`
1. **`workflow_dispatch`:** Può essere invocato via REST API usando `GITHUB_TOKEN` (richiede `permissions: actions: write`); innesca sempre il nuovo giro.
2. **`repository_dispatch`:** Può essere invocato via REST API usando `GITHUB_TOKEN` (richiede `permissions: contents: write`); innesca sempre il workflow bersaglio.
3. **`pull_request` (attività `opened`, `synchronize`, `reopened`):** Se una PR viene aperta o aggiornata tramite `GITHUB_TOKEN`, l'evento `pull_request` viene scatenato, ma il giro viene inserito in stato di attesa approvazione manuale (*approval required*) da parte di un utente con permessi di scrittura prima di essere eseguito. Le altre attività (`labeled`, `closed`, ecc.) non innescano alcun giro.

### Comportamento con Token Personale (PAT) o GitHub App
Quando le azioni (push, creazione rami, apertura issue/PR, commenti, ecc.) vengono eseguite autenticandosi con un **Personal Access Token (PAT)** o un token di **GitHub App**:
- La regola anti-loop del `GITHUB_TOKEN` **non si applica**.
- Tutti i workflow configurati per quegli eventi si avviano automaticamente e normalmente, senza restrizioni né richieste di approvazione.

**Fonti:**
- https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication#using-the-github_token-in-a-workflow

## 6. Variabili di Actions (Actions Variables)

### Lettura e scrittura via CLI e REST API
- **CLI (`gh variable`):**
  ```bash
  # Elencare le variabili del repository
  gh variable list --repo <proprietario>/<repo>

  # Leggere il valore di una variabile
  gh variable get QUOTA_BOTTEGA --repo <proprietario>/<repo>

  # Creare o aggiornare una variabile a livello di repository
  gh variable set QUOTA_BOTTEGA --body "10" --repo <proprietario>/<repo>

  # Eliminare una variabile
  gh variable delete QUOTA_BOTTEGA --repo <proprietario>/<repo>
  ```
- **REST API:**
  - Elenco: `GET /repos/{owner}/{repo}/actions/variables`
  - Lettura: `GET /repos/{owner}/{repo}/actions/variables/{name}`
  - Creazione: `POST /repos/{owner}/{repo}/actions/variables` con body JSON `{"name": "QUOTA_BOTTEGA", "value": "10"}`
  - Modifica: `PATCH /repos/{owner}/{repo}/actions/variables/{name}` con body JSON `{"name": "QUOTA_BOTTEGA", "value": "15"}`
  - Eliminazione: `DELETE /repos/{owner}/{repo}/actions/variables/{name}`

### Il `GITHUB_TOKEN` può scriverle?
- **NO.** Il `GITHUB_TOKEN` di un workflow **non ha i permessi per creare o modificare le variabili** tramite l'endpoint `/repos/{owner}/{repo}/actions/variables`, anche impostando esplicitamente `permissions: actions: write`. L'API risponde con `403 Forbidden`.
- **Come leggerle nel workflow:** All'interno del workflow possono essere lette passivamente senza chiamate API tramite il contesto nativo: `${{ vars.NOME_VARIABILE }}`.
- **Che token serve per scriverle via API o `gh`:**
  - Un **Personal Access Token (classic)** con scope `repo` (per repo privati).
  - Un **Fine-grained Personal Access Token** con permesso repository **Variables: Read and write**.
  - Oppure un token di **GitHub App** con permesso repository **Variables: Read and write**.

**Fonti:**
- `gh variable --help`, `gh variable set --help`, `gh variable get --help`
- https://docs.github.com/en/rest/actions/variables

## 7. Limiti (Rate Limits)

### Limiti secondari sulla creazione di contenuti
Per prevenire abusi e spam, le richieste che creano contenuti o inviano notifiche (issue, commenti, pull request, push di commit) sono soggette a limiti secondari più severi:
- **Limite al minuto:** Massimo **80 richieste di creazione contenuto al minuto**.
- **Limite all'ora:** Massimo **500 richieste di creazione contenuto all'ora**.
- **Linee guida di GitHub:**
  - Eseguire le richieste mutative in modo sequenziale (non concorrente).
  - Attendere **almeno 1 secondo** tra chiamate mutative consecutive (`POST`, `PATCH`, `PUT`, `DELETE`).
  - Massimo **100 richieste concorrenti** simultanee (REST + GraphQL).
  - In caso di superamento viene restituito HTTP `403` o `429` (spesso con header `Retry-After`).

### Limiti orari primari dell'API (REST e GraphQL)
- **Personal Access Token (PAT classic o fine-grained per account personale):**
  - REST API: **5.000 richieste all'ora**.
  - GraphQL API: **5.000 punti all'ora**.
- **`GITHUB_TOKEN` (in GitHub Actions):**
  - REST API: **1.000 richieste all'ora per repository**.
  - GraphQL API: **1.000 punti all'ora per repository**.

**Fonti:**
- https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api
- https://docs.github.com/en/graphql/overview/resource-limitations

## 8. Eventi delle Issue e delle PR per i Workflow

### Dichiarazione degli eventi nei workflow
- **`issues: labeled`:**
  ```yaml
  on:
    issues:
      types: [labeled]
  ```
- **`issue_comment: created`:**
  ```yaml
  on:
    issue_comment:
      types: [created]
  ```
- **`pull_request_review`:**
  ```yaml
  on:
    pull_request_review:
      types: [submitted, edited, dismissed]
  ```
- **`projects_v2_item` (vale per account personali?):**
  - **NO.** L'evento `projects_v2_item` non vale per gli account personali.
  - È un evento webhook supportato **esclusivamente a livello di organizzazione** (`organization-level projects`) e per GitHub Apps. Inoltre non è un trigger nativo diretto di GitHub Actions (`on: projects_v2_item` non esiste per i workflow di repository).

### Dati disponibili nel contesto
- **Identità dell'autore del commento:**
  - Login utente: `github.event.comment.user.login` (stringa con il nome utente).
- **Associazione dell'autore (`author_association`):**
  Disponibile in:
  - `github.event.comment.author_association` (per il commento)
  - `github.event.issue.author_association` (per l'autore della issue)
  - `github.event.review.author_association` (per il revisore della PR)
  - `github.event.sender.author_association` (per l'utente che ha scatenato l'evento)

Valori restituiti da GitHub per `author_association`:
1. `OWNER`: proprietario del repository o dell'account.
2. `COLLABORATOR`: collaboratore invitato con permessi espliciti di accesso al repository.
3. `MEMBER`: membro dell'organizzazione a cui appartiene il repository.
4. `CONTRIBUTOR`: utente con commit precedenti nel repository, non membro né collaboratore.
5. `FIRST_TIME_CONTRIBUTOR`: utente che apre il suo primo contributo nel repository.
6. `FIRST_TIMER`: utente al suo primo contributo assoluto su GitHub.
7. `NONE`: nessun ruolo o contributo pregresso con il repository.
8. `MANNEQUIN`: profilo placeholder segnaposto (es. post-migrazione).

**Fonti:**
- https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows
- https://docs.github.com/en/webhooks/webhook-events-and-payloads#projects_v2_item
- https://docs.github.com/en/graphql/reference/enums#commentauthorassociation

## 9. Runner Self-Hosted per un Account Personale

### Registrazione per repo o per account?
- **Esclusivamente per singolo repository.**
- Negli account personali non è supportata la registrazione di runner a livello di account (la registrazione a livello di account o gruppo runner è disponibile unicamente per Organizzazioni ed Enterprise).
- Endpoint REST: `POST /repos/{owner}/{repo}/actions/runners/registration-token`.

### Etichette (Labels)
- **Etichette predefinite assegnate dal runner:**
  - `self-hosted`
  - Sistema operativo: `linux`, `macos` o `windows`
  - Architettura CPU: `x64`, `arm` o `arm64`
- **Etichette personalizzate:**
  - Aggiungibili durante la configurazione (`./config.sh --labels bottega,lavorante`) o modificabili dall'interfaccia/API.
  - Selezione nel workflow: `runs-on: [self-hosted, linux, bottega]`.

### Runner come servizio con un utente Unix scelto
Nella cartella del runner scaricato su Linux:
```bash
# Installazione come servizio specificando l'utente di sistema desiderato
sudo ./svc.sh install <utente_unix>

# Avvio del servizio
sudo ./svc.sh start

# Verifica dello stato
sudo ./svc.sh status

# Arresto e disinstallazione
sudo ./svc.sh stop
sudo ./svc.sh uninstall
```

### Quanti job alla volta?
- **Uno solo alla volta** per ogni istanza dell'applicazione runner.
- Un runner non accetta job in parallelo. Se arrivano più job contemporaneamente, vengono eseguiti in sequenza (uno alla volta). Per eseguire più job concorrenti sulla stessa macchina fisica occorre installare più istanze distinte del runner in directory separate.

### Comportamento a runner spento e timeout in coda
- Se nessun runner con le etichette richieste è online, il job rimane nello stato **`Queued`** (in coda).
- **Tempo massimo di permanenza in coda:** **24 ore**. Se il runner non torna online entro 24 ore, GitHub annulla automaticamente il job contrassegnandolo come fallito per timeout.

**Fonti:**
- https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/about-self-hosted-runners
- https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/configuring-the-self-hosted-runner-application-as-a-service

## 10. Firme dei Commit con Chiave SSH

### Visualizzazione del commit firmato SSH come "Verified"
Perché GitHub mostri il badge verde **Verified**:
1. **Configurazione Git locale:**
   ```bash
   # Indicare a Git di usare SSH per le firme
   git config --global gpg.format ssh

   # Specificare la chiave pubblica SSH da usare
   git config --global user.signingkey ~/.ssh/id_ed25519.pub

   # Abilitare la firma predefinita per tutti i commit
   git config --global commit.gpgsign true
   ```
2. **Caricamento della chiave su GitHub:**
   - Andare su **Settings > SSH and GPG keys > New SSH key**.
   - Nel campo **Key type**, selezionare tassativamente **Signing Key** (non *Authentication Key*).
   - *(Se la stessa chiave SSH viene usata sia per autenticare il push sia per firmare, deve essere caricata due volte: una come Authentication Key e una come Signing Key).*
3. **Corrispondenza Email:**
   L'email configurata nell'autore del commit (`git config user.email`) deve coincidere con una delle email verificate nell'account GitHub.

### Regole del ramo / rulesets per commit firmati su repo privato di account personale
- **Account personale gratuito (GitHub Free):**
  - **NON disponibili** su repository privati. Le regole di protezione del ramo e i Rulesets non sono attivabili sui repo privati del piano Free.
- **Account personale a pagamento (GitHub Pro):**
  - **DISPONIBILI** su repository privati. Sia come Branch Protection classica (Settings > Branches > *Require signed commits*), sia tramite i nuovi **Rulesets** (Settings > Rules > Rulesets > aggiungi regola *Require signed commits*).

## 11. `gh` per un Altro Utente Unix

### Dove `gh auth login` salva il token
1. **Keyring di sistema (predefinito):**
   Su Linux tenta di memorizzare il token tramite il Secret Service API / DBus keyring (GNOME Keyring, KWallet).
2. **File di testo in fallback (o con `--insecure-storage`):**
   Se non è presente un credential manager o se invocato con `--insecure-storage`, il token viene salvato in chiaro nel file:
   `~/.config/gh/hosts.yml` (rispettando `$XDG_CONFIG_HOME/gh/hosts.yml` o `$GH_CONFIG_DIR/hosts.yml`).
   La voce salvata ha la struttura:
   ```yaml
   github.com:
       user: <utente>
       oauth_token: gho_...
       git_protocol: https
   ```
   Se il token è nel keyring di sistema, `hosts.yml` memorizza solo il nome utente e il protocollo, omettendo la chiave `oauth_token`.

### `gh auth token`
Stampa direttamente su standard output il token di autenticazione attualmente in uso per l'host:
```bash
gh auth token
# per un host o utente specifico:
gh auth token --hostname github.com --user <utente>
```

### `GH_TOKEN`
Variabile d'ambiente (`GH_TOKEN` o `GITHUB_TOKEN`):
- Ha la **priorità massima** rispetto a qualsiasi credenziale salvata in keyring o in `hosts.yml`.
- Permette l'esecuzione completamente stateless e headless da script o da un altro utente Unix:
  ```bash
  export GH_TOKEN="ghp_..."
  gh repo list
  ```

### Usare un token per spingere con Git senza scriverlo nella configurazione del repo
1. **Configurazione globale con `gh auth setup-git` (consigliata per `gh`):**
   Eseguire una volta:
   ```bash
   gh auth setup-git
   ```
   Configura il credential helper globale di Git per delegare le credenziali a `gh`:
   `credential.https://github.com.helper = !gh auth git-credential`.
   In questo modo ogni `git push` interroga dinamicamente `gh` (e quindi la variabile `GH_TOKEN` o il keyring), senza inserire alcuna credenziale nel file `.git/config` del repository.
2. **Iniezione estemporanea tramite header HTTP per singolo comando:**
   ```bash
   git -c http.extraHeader="AUTHORIZATION: bearer $GH_TOKEN" push origin <ramo>
   ```
   Non modifica la configurazione del repository e non persiste su disco.
3. **Credential helper inline monouso per singolo comando:**
   ```bash
   git -c credential.helper='!f() { echo "username=x-access-token"; echo "password='$GH_TOKEN'"; }; f' push origin <ramo>
   ```

**Fonti:**
- `gh help environment`, `gh auth login --help`, `gh auth token --help`, `gh auth setup-git --help`
- https://cli.github.com/manual/gh_auth_setup-git

## 12. Commenti con un Segno Nascosto (`<!-- … -->`)

### Restano nel corpo restituito dall'API?
- **SÌ.** Il campo `body` restituito sia dall'API REST (`GET /repos/{owner}/{repo}/issues/comments/{comment_id}`) sia dall'API GraphQL (`issueComment.body`) riporta integralmente il testo Markdown grezzo inserito dall'autore, preservando intatti i tag `<!-- commento nascosto -->`.

### Si vedono nell'interfaccia?
- **NO.** Il motore di rendering Markdown di GitHub interpreta `<!-- … -->` come commento HTML standard e lo rimuove dalla vista visualizzata agli utenti nel browser. È visibile solo entrando in modalità di modifica del commento ("Edit") o ispezionando il sorgente Markdown grezzo.

**Fonti:**
- https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax
- https://docs.github.com/en/rest/issues/comments#get-an-issue-comment
